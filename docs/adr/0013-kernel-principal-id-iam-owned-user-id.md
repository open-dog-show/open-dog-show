# Kernel context-neutral `PrincipalId`; IAM-owned `UserId`

> Resolves issue #92. Applies [ADR-0011](0011-context-specific-identity-ports-for-iam-acl.md) (context-specific identity ports) at the kernel/identity-owner boundary, and refines [ADR-0005](0005-data-ownership-scopes-and-rls-keys.md)'s `user_id` naming.

## Context

ADR-0011 forbids a shared `User`-with-roles model in domain layers and mandates that each downstream context define its own narrow identity port (`AuthenticatedShowSecretary`, etc.). Yet `UserId` — the identity owner's own identifier — was defined in `@ods/kernel`'s domain layer and imported _from the kernel_ by `@ods/iam` (its `User`, `UserRepository`, `RoleGrant`, `RoleGrantRepository`) and by `@ods/sample`. The identity owner importing its own id from the shared kernel is an ownership inversion: it tells every future contributor that identity ids live in the kernel, and invites the next identity-adjacent id to land there too. ADR-0011's context-specific ports and the IAM ACL adapter are otherwise unimplemented (tracked in #15 / #80).

The kernel's `TransactionScope` genuinely needs _some_ identifier to set the `app.user_id` RLS session variable (ADR-0005), so the question is not "remove the id" but "what do we name it, and who owns it?"

## Decision

- The kernel owns a **context-neutral `PrincipalId`** — the abstract "actor in this transaction," used only for RLS plumbing (`TransactionScope` sets `app.user_id` from it). "Principal" is the standard access-control term for the actor on whose behalf an operation runs, independent of which identity system produced it. `PrincipalId` is a kernel plumbing type, **not** a ubiquitous-language term: like `TenantId` and the other branded `*Id` types, it is intentionally absent from `CONTEXT.md`.
- `@ods/iam` owns **`UserId`** — its concrete platform-account identifier — defined in `@ods/iam`'s domain layer, no longer in the kernel. `@ods/iam`'s `User` / `UserRepository` / `RoleGrant` / `RoleGrantRepository` import `UserId` from their own package. `TenantId` stays in the kernel (ADR-0005 treats `tenant_id` as a cross-cutting RLS key, not a Club or IAM concept); only `UserId` moves.
- `TransactionScope` carries `PrincipalId` (not `UserId`) in its `tenant` and `exhibitor` variants; the `platform` variant carries no id. The kernel-internal `RlsKeys` field is renamed `userId` → `principalId` so the kernel's TypeScript surface says "principal" everywhere. The **SQL wire name is unchanged**: the GUC `app.user_id` and the column `user_id` are on-the-wire/protocol names below the ubiquitous language, exactly like `tenant_id`; only the string literal is kept, with a one-line comment tying it to `PrincipalId` (see the cross-reference note added to ADR-0005).
- `PrincipalId` is a deliberately **distinct brand** from `UserId`. In the current system a `PrincipalId` **always carries a `User.id`** — the value is identical and `User → PrincipalId` is a cast (`asPrincipalId(user.id)`), not a translation. The value of the distinct brand is precisely that it **forces a cast at the ACL boundary**: a `UserId` can never silently flow into a `TransactionScope` without someone writing `asPrincipalId(...)` at the context edge. That cast is the seam. No discriminated union of principal kinds is introduced — there is one principal kind today (a `User`); a future non-User principal (a service account, an NCO system) would produce a `PrincipalId` through its own adapter without the kernel changing, at which point the union can be reconsidered.
- The `User → PrincipalId` cast and the suspended-account rejection (`user.status === 'Active'`) happen at the **`apps/api` composition root**, where the `TransactionScope` is built — a single, clearly-commented cast site that the future IAM ACL adapter (#15 / #80) will grow into. **No named ACL adapter package is built in #92.** The per-context `AuthenticatedX` ports (ADR-0011) and the full `User` + `Role Grant`s → port translation remain the IAM ACL epic (#15 / #80); #92 establishes only the `PrincipalId`/`UserId` ownership split and the cast seam.
- The dead, kernel-exported `ExhibitorId` brand is **removed**. `CONTEXT.md` defines an `Exhibitor` as a capability a `User` holds ("the account holder who enters a Dog"), not a distinct identity; `CONTEXT-MAP.md` states "Exhibitor is the default capability of any Active User." There is no "exhibitor account" separate from a `User`, so a separate `ExhibitorId` brand is conceptually wrong as well as unused. The exhibitor-scope actor is the `User`, typed `PrincipalId` in the kernel. A future Entries-context identity port is `AuthenticatedExhibitor` living in the Entries context's domain layer (ADR-0011), not a kernel `ExhibitorId`.

## Considered options

- **Accept the drift: keep a context-neutral `UserId` branded string in the kernel; amend ADR-0011 to permit it while still forbidding the `User`-with-roles object.** A bare branded `UserId` is not the `User`-with-roles evil ADR-0011 forbids — it carries no roles, status, or IAM behaviour, and is structurally identical to the `TenantId` ADR-0005 defends. Rejected: the leak is _active_ (the identity owner imports its own id from the kernel), the fix is cheap today (two consumers), and the cost grows monotonically as more contexts adopt the pattern. Amending an ADR to bless the very slope it was written to prevent, for a naming cosmetic, costs more than honouring it now.
- **Name the kernel id `ActorId` or `SubjectId`.** `SubjectId` collides with `User.externalSubject` (the identity-provider subject claim); a second "subject" meaning would be an overloaded-term smell. `ActorId` risks blurring with the ADR-0011 context-specific role ports (`AuthenticatedShowSecretary` etc.), which _are_ domain actors. `PrincipalId` is the access-control term and is distinct from every domain role word.
- **Build a minimal named `User → PrincipalId` adapter as a real seed in #92.** Rejected: an adapter in `@ods/iam` would make every downstream context depend on `@ods/iam` (a cross-context import violation, ADR-0004/0006), and a named helper in `apps/api` is indistinguishable from a clearly-commented cast site. Naming a "principal adapter" before the per-context ports exist is premature framing; defer to #15/#80.
- **Keep `ExhibitorId` and use it (`Entry.exhibitorId`).** Rejected: contradicts ADR-0011 (the context-specific port lives in the downstream context, not the kernel) and contradicts "Exhibitor is a capability, not a distinct identity."
- **Rename the SQL GUC/column to `principal_id`.** Rejected for #92: high-churn, security-adjacent (migrations, RLS predicates), and unnecessary — the wire name sits below the ubiquitous language, like `tenant_id`.

## Consequences

- The kernel's public surface exports `PrincipalId`/`asPrincipalId` and no longer exports `UserId`/`asUserId` or `ExhibitorId`/`asExhibitorId`. Downstream context domain layers that need the RLS foreign-id reference `PrincipalId`; none import `UserId` from the kernel.
- `@ods/iam` gains its own `domain-ids.ts` owning `UserId`/`asUserId`; the kernel's domain layer stays ORM-free and now identity-vocabulary-free.
- A future reader of ADR-0005's 2026-08-22 amendment ("renamed so the ubiquitous-language term _User_ is used consistently") who then sees `PrincipalId` in the kernel needs this ADR to resolve the apparent contradiction: that amendment's rationale governs the _SQL wire name_, which stayed `user_id`; the kernel's _type_ is `PrincipalId` per this decision. A cross-reference note is added to ADR-0005 to that effect.
- The word "exhibitor" now names two distinct things — a domain role (Entries & Registration) and a data-ownership RLS scope (ADR-0005) — which also holds for "tenant". A disambiguation note is added to `CONTEXT.md`'s `Exhibitor` entry; the scope-kind labels themselves are unchanged (they are ADR-0005 RLS regimes, shared with `EventScope`).
- The full IAM ACL — per-context `AuthenticatedX` ports and a named adapter — remains to be built (#15 / #80); #92 leaves a single cast site at `apps/api` as the seed. `PrincipalId` is a branded string with no validation, identical in shape to the other id brands.
